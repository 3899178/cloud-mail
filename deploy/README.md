## Backup, rollout and rollback

Controller owns all actual SSH/Cloudflare/GitHub operations. `ops.mjs` performs no implicit SSH and never evaluates shell command strings. Commands below are **operator-only**, with private config files outside git. Linux owner/mode checks protect mutations; Windows actual backup should use the controller's owner-ACL/DPAPI adapter. This candidate does not read that private adapter or credentials.

`node deploy/ops.mjs backup /PRIVATE/backup-config.json` invokes eight explicit collector executable/argument arrays from the operator's config and captures their stdout only into0700/0600 files: `worker-version`, `worker-source`, `worker-assets`, `d1-full-sql`, `kv-data`, `kv-config`, `caddy`, `service-config`. Collectors must capture actual deployment/version/routing/settings/source plus the complete reachable asset graph, full D1 SQL, paginated KV values/metadata/expiry and configuration, current Caddy and complete service configuration. Supply auth through the private environment/managed CLI, never collector arguments. A file-exporting command needs a private adapter that emits the exported bytes, not a success message. Version is collected twice to reject deployment drift. The tool hashes and roundtrips every captured file and writes `backup.json` only after complete success. Restore the D1 SQL in a separate temporary database and verify asset/KV inventories before accepting it. Capture service SQLite and retained attachments separately with a consistent SQLite backup/snapshot; never copy a live WAL database alone. A generic collector result is **not independently verified provider evidence**: the controller must review actual contents and restoration.

Backup config fields: `output`, `target` (`preview`/`production`), full40hex `source`, `currentImage` digest, `collectors` map of `{program:<absolute executable>,args:[...]}`. On first install only, use `currentImage:"absent",firstInstall:true` after inventory proves absence. Fresh backup must be made immediately before mutation; old owner-protected baselines remain preserved. No backup or acceptance receipt is generated by a fixture.

`node deploy/ops.mjs dry-run /PRIVATE/rollout-config.json` verifies freshness (maximum1hour), target/source/image binding, every backup file hash, all acceptance gates and expected current Caddy SHA. Required acceptance fields are documented in `gates.mjs`; the controller supplies actual reviewed Linux/image/resource/rollback/legacy/tenant/provider/proxy-redaction/other-app evidence. Preserve the actual receipt files and run URLs alongside it. `rollout-config` has `backup`, `acceptance`, `privateRoot`, `target`, `source`, `image`, `caddyPath`, `expectedCaddySha256`, `hostname`, `caddyContainer`. Private runtime data/environment must already be securely provisioned and quota-validated. Ordinary test output cannot stand in for acceptance.

After review, `node deploy/ops.mjs rollout /PRIVATE/rollout-config.json --apply` validates Compose/pulls the CI-built image, validates a copied candidate with the **existing Caddy executable**, rechecks fresh evidence/current Caddy, saves a recovery intent, starts only the mail-sync service and atomically updates the host Caddy file. Caddy may bind-mount the old inode, so reload uses the separately validated in-container candidate; a future container restart reads the new host file. No other host stanza is changed. Archive prior per-release receipt/release.env filenames privately before starting a subsequent release. No schema operation is automatic. Apply additive Worker/D1 migrations explicitly only after the same fresh gate; never run old `/api/init` or destructive schema resets.

Check `docker compose ... ps`, `/usr/local/bin/supervisor health`, protected unauthorized401 and signed tenant requests through the **actual existing Caddy/Worker route**, and compare all nine apps/host resources/Caddy prefix hashes before and after. Keep production blocked if a gate fails.

`node deploy/ops.mjs rollback /PRIVATE/rollback-config.json` is a dry run; add `--apply` only as operator. Fields: `privateRoot`, `target`, `currentImage`, `caddyPath`, `caddyContainer`. It verifies rollout/Caddy hashes, returns to the previous **whole Node+helper image**, and restores exactly the previous Caddy bytes. On first install rollback stops the new service. It never deletes mail, restores old SQLite over current mail, or runs a backwards schema migration; existing schema must be1. Node/helper delta contracts are incompatible with older standalone Node: upgrade/rollback them together. A changed unrelated Caddy configuration causes refusal rather than overwrite. Failure after partial mutation uses the persisted recovery intent, not an assumption that rollout finished. Actual rollback rehearsal remains mandatory before production.

Rollout and rollback cooperate on an exclusive `<Caddyfile>.cloud-mail.lock`, released on success or failure. Other configuration operators should honor that same lock. Rollback compares the exact initially observed live Caddy hash immediately before rename and refuses a concurrent edit; it does not reload stale bytes after refusal. A process-killed stale lock needs operator verification that the original operation has stopped before removal. The lifecycle CI smoke seeds two paused tenant accounts, two retained messages/checkpoints, encrypted vault records and nontrivial attachments through the production store, then verifies logical contents/decryption/SHA after helper crash/restart, stop/start and final stop using the exact runtime image. This fixture does not yet demonstrate draining an in-flight business request; that runtime evidence remains pending.
